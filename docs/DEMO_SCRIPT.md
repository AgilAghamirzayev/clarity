# Clarity: fresh processing demonstration

Aim for three minutes after preflight. Processing time is variable; the schedule is a rehearsal plan. Use an isolated guest workspace with the API, worker and models running. Keep the current pitch open as a clearly labeled prepared fallback.

## Preflight

- Open the guest workspace and select **Try fresh analysis** to reach Conversations directly. The guided tour is optional.
- Check the API and worker, available local models, guest upload allowance and a generated sample recording.
- Use **Analyze sample call** once before presenting to confirm actual completion. A preflight run does not make the later run fresh; start another job during the demonstration.
- Keep a pending proposal available for a new guest decision. Use owner `Demo engineering reviewer` and rationale `Investigate the cited customer report and verify the cause before changing the service.`

If the new job is still processing, show its actual status. Continue using an explicitly labeled prepared example or extend the time slot. Do not substitute a prepared record and describe it as the new result.

## Two-minute alternative

Start the fresh job immediately, explain the task while it runs, then inspect the new result and save a review. Skip the outcome screen and guided tour. If the job cannot finish within the slot, disclose the pending state and show the prepared fallback.

## Prepared fallback and boundaries

The payment catalog has two calls from one fictional customer, not two independent affected customers. Stored analyses use an older prompt and include editorial titles and documented sample corrections. Seeded decisions illustrate states. A screenshot is a prepared capture, not a live interaction.

The positive sample demonstrates a no-issue example, not an accuracy estimate. A result with rejected findings requires review and must not be presented as a confirmed no-problem call. Before/after outcome windows are observational and do not prove the decision improved the business.
